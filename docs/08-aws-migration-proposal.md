# ข้อเสนอการย้ายระบบ score-app ไปยัง AWS

> เอกสารฉบับร่างสำหรับหารือกับฝ่ายผู้ใช้งาน — จัดทำ 2026-10-06
> สถานะ: **ข้อเสนอ (ยังไม่เริ่มทำ)** — รอการตัดสินใจร่วมกัน

---

## 1. สรุปสำหรับผู้บริหาร (Executive Summary)

ปัจจุบันระบบ score-app ทำงานอยู่บน **Microsoft Azure** และใช้งานได้ดี
มีความจำเป็นต้องย้ายระบบไปอยู่บน **Amazon Web Services (AWS)** ตามนโยบาย

ข่าวดีคือ ระบบนี้ถูกออกแบบมาให้ **ย้ายง่าย** ตั้งแต่ต้น (ใช้ Docker + ฐานข้อมูลมาตรฐาน)
จึง **ไม่ต้องเขียนโปรแกรมใหม่** — เป็นการย้าย "ที่อยู่" ของระบบเป็นหลัก

แนวทางที่เสนอเน้น **ประหยัดค่าใช้จ่ายสูงสุด** เพราะระบบใช้งานเป็นครั้งคราว (เฉพาะช่วงมีการแข่งขัน)
โดยจะ **ทดสอบบน AWS ให้มั่นใจก่อน (UAT)** แล้วจึงค่อยสลับมาใช้จริงและปิดฝั่ง Azure ภายหลัง

---

## 2. ระบบปัจจุบันเป็นอย่างไร

| หัวข้อ | รายละเอียด |
|--------|-----------|
| ลักษณะงาน | เว็บให้คะแนนการแข่งขัน (กรรมการกรอกคะแนน → รวมผล → จัดอันดับ) |
| ปริมาณการใช้ | โหลดต่ำ (กรรมการ + แอดมิน รวม < 10 คน, ทีม ≤ 20) ใช้เฉพาะช่วงมีงาน |
| โครงสร้าง | โปรแกรมถูกแพ็กเป็น "กล่องสำเร็จรูป" (Docker) 1 กล่อง เสิร์ฟทั้งหน้าเว็บและระบบหลังบ้าน |
| ฐานข้อมูล | SQLite — ไฟล์ฐานข้อมูลไฟล์เดียว (ข้อมูลไม่เยอะ ระดับไม่กี่ MB) |
| ที่อยู่ปัจจุบัน | Azure Container Apps + ที่เก็บไฟล์ Azure Files |

**จุดสำคัญ:** ตัวโปรแกรมไม่ได้ผูกติดกับ Azure โดยตรง สิ่งที่ผูกกับ Azure มีแค่ส่วน "โครงสร้างพื้นฐาน" (ที่รันและที่เก็บไฟล์) และ "ระบบ deploy อัตโนมัติ" เท่านั้น

## 3. เป้าหมายและเงื่อนไขที่ตกลงกัน

1. ✅ **ต้องย้ายไป AWS** (เงื่อนไขบังคับ)
2. 💰 **ประหยัดค่าใช้จ่ายสูงสุด** — ระบบใช้งานแค่บางครั้ง ไม่ควรเสียเงินตอนไม่มีคนใช้
3. 📦 **ข้อมูลเดิมไม่จำเป็นต้องย้ายทั้งหมด** — ย้ายเฉพาะที่จำเป็น หรือเริ่มใหม่ได้
4. 🧪 **ทำ UAT บน AWS ก่อน** แล้วค่อยสลับมาใช้จริง (cut over) จากนั้นปิดฝั่ง Azure

## 4. ทางเลือกบน AWS (เปรียบเทียบ)

> หลักคิดสำคัญเรื่องค่าใช้จ่าย: บริการที่ "เปิดทิ้งไว้ตลอด 24 ชม." จะมีค่าใช้จ่ายรายเดือนคงที่
> ส่วนบริการที่ "ปิดได้ตอนไม่ใช้" จะเสียเงินเฉพาะตอนใช้งานจริง — ตอบโจทย์ข้อ 2 มากกว่า

| ทางเลือก | เสียเงินตอนไม่ใช้งาน | เก็บแบบ SQLite เดิมได้ | ความซับซ้อนในการตั้งค่า | เหมาะกับเราไหม |
|---------|:---:|:---:|:---:|:---:|
| **A. ECS Fargate + EFS** (เสนอ) | **เกือบ 0** (จ่ายแค่ค่าเก็บไฟล์) | ✅ ได้ | ปานกลาง | ⭐ แนะนำ |
| B. App Runner | มี (เปิดตลอด) | ❌ ไม่ได้ | ง่าย | ไม่ตอบโจทย์ประหยัด |
| C. ECS/App Runner + ฐานข้อมูล RDS | มีค่าคงที่ ~$15+/เดือน | — (เปลี่ยนเป็น PostgreSQL) | สูง | ไม่ตอบโจทย์ประหยัด |

### ทางเลือกที่เสนอ: A — ECS Fargate + EFS

- รันโปรแกรม (กล่อง Docker เดิม) บน **ECS Fargate** — ไม่ต้องดูแลเครื่อง server เอง
- เก็บไฟล์ฐานข้อมูลบน **EFS** (ที่เก็บไฟล์ถาวรของ AWS) — ข้อมูลไม่หายแม้ปิดระบบ
- **ปิดระบบได้ตอนไม่มีงาน** (ตั้งจำนวนเครื่องเป็น 0) → ไม่เสียค่าประมวลผลเลย เสียแค่ค่าเก็บไฟล์หลักบาท/เดือน
- ก่อนมีงานแข่งขัน → "เปิดระบบ" (ตั้งเป็น 1 เครื่อง) ใช้เวลาไม่กี่สิบวินาที; เสร็จงาน → "ปิดระบบ"

**ทำไมไม่เลือก B หรือ C:**
- **B (App Runner):** ตั้งค่าง่ายที่สุด แต่ต้องเปิดเครื่องขั้นต่ำ 1 เครื่องตลอดเวลา (เสียเงิน 24 ชม.) และแนบที่เก็บไฟล์ถาวรไม่ได้ → ใช้ SQLite ไม่ได้
- **C (ฐานข้อมูล RDS):** ทนทานและขยายได้ดีที่สุด แต่ฐานข้อมูลต้องเปิดตลอดเวลา = ค่าใช้จ่ายคงที่รายเดือน ขัดกับเป้าหมายประหยัด และต้องแปลงฐานข้อมูล (เพิ่มงาน + ความเสี่ยง)

## 5. ค่าใช้จ่าย (ประมาณการเบื้องต้น)

> ⚠️ เป็นการประมาณการคร่าว ๆ เพื่อการตัดสินใจ ตัวเลขจริงต้องยืนยันด้วย
> [AWS Pricing Calculator](https://calculator.aws/) และตั้ง Budget Alert หลังเริ่มใช้งาน

| รายการ | ตอนไม่มีงาน (ปิดระบบ) | ตอนมีงาน (เปิดใช้) |
|--------|:---:|:---:|
| ค่าประมวลผล (Fargate) | 0 บาท | คิดตามชั่วโมงที่เปิด (หลักบาท–สิบบาท/วันงาน) |
| ค่าเก็บไฟล์ฐานข้อมูล (EFS) | หลักบาท/เดือน (ข้อมูลไม่กี่ MB) | เท่าเดิม |
| ค่าเก็บ Docker image (ECR) | หลักบาท/เดือน | เท่าเดิม |
| **รวมโดยประมาณ** | **ไม่กี่บาท/เดือน** | **เพิ่มเฉพาะช่วงจัดงาน** |

**สรุป:** ถ้าปีหนึ่งจัดงานไม่กี่ครั้ง ค่าใช้จ่ายรวมทั้งปีจะต่ำมาก เพราะช่วงที่ไม่มีงานแทบไม่เสียเงินเลย

## 6. สิ่งที่ต้องทำ (ขอบเขตงาน)

### 6.1 งานฝั่งโครงสร้างพื้นฐาน (AWS) — งานหลัก
- สร้างบัญชี/สิทธิ์การใช้งาน AWS และระบบเครือข่าย (VPC, Subnet, Security Group)
- สร้างที่เก็บ Docker image (ECR)
- สร้างที่เก็บไฟล์ถาวร (EFS) สำหรับฐานข้อมูล
- สร้างบริการรันโปรแกรม (ECS Fargate) + เปิดการเข้าถึงผ่านเว็บ (HTTPS)

### 6.2 งานฝั่งโปรแกรม — เล็กน้อย
- ปรับไฟล์ตั้งค่า Docker เล็กน้อย (ชี้ที่เก็บไฟล์ไปยัง EFS) — **ไม่แก้ตรรกะโปรแกรม**
- จัดการเรื่องการล็อกไฟล์ฐานข้อมูลให้เหมือนเดิม (ใช้ 1 เครื่องเท่านั้น เหมือนที่ Azure ทำอยู่แล้ว)

### 6.3 งานระบบ deploy อัตโนมัติ (CI/CD)
- เขียนขั้นตอน deploy อัตโนมัติใหม่สำหรับ AWS (แทนของ Azure เดิม)
- ใช้วิธีเชื่อมต่อแบบปลอดภัย (ไม่เก็บรหัสลับถาวร)

### 6.4 เครื่องมือ "เปิด–ปิดระบบ"
- ทำปุ่ม/สคริปต์ให้ทีมสั่งเปิดระบบก่อนงาน และปิดหลังงานได้ง่าย

### 6.5 เอกสาร
- อัปเดตคู่มือ deploy และคู่มือทีมให้ตรงกับ AWS

## 7. ข้อควรทราบ / ข้อจำกัด (ต้องสื่อสารกับผู้ใช้งาน)

1. **ต้อง "เปิดระบบ" ก่อนใช้งาน**
   เพื่อประหยัดค่าใช้จ่าย ระบบจะถูกปิดตอนไม่มีงาน ก่อนจัดการแข่งขันต้องสั่งเปิดล่วงหน้า (ไม่กี่สิบวินาที)
   → หากต้องการให้ระบบ "ออนไลน์ตลอดเวลา เข้าได้ทันที" จะมีค่าใช้จ่ายคงที่รายเดือนเพิ่ม (ต้องตัดสินใจ)

2. **ที่อยู่เว็บ (URL) จะเปลี่ยน**
   ลิงก์เดิมของ Azure จะใช้ไม่ได้หลัง cut over ต้องแจกลิงก์ใหม่ให้กรรมการ
   → หากต้องการใช้ชื่อโดเมนของตัวเอง (เช่น score.ชื่อองค์กร.com) สามารถทำเพิ่มได้ (ต้องมีโดเมน)

3. **ลิงก์กรรมการจะถูกสร้างใหม่** หากเริ่มฐานข้อมูลใหม่บน AWS → ต้องแจกลิงก์ใหม่

4. **ยังคงใช้ได้ทีละ 1 เครื่อง** (เหมือน Azure เดิม) เพียงพอกับปริมาณงานปัจจุบัน แต่ไม่ได้ออกแบบมารับโหลดสูงพร้อมกันจำนวนมาก

## 8. แผนการย้าย (แบบ UAT ก่อน แล้วค่อย Cut Over)

```
ระยะที่ 1: เตรียม (ไม่กระทบ Azure)
  └─ สร้างระบบบน AWS ขนานไปกับ Azure (Azure ยังใช้งานได้ปกติ)

ระยะที่ 2: UAT / ทดสอบ
  └─ ได้ URL ของ AWS → ทีมผู้ใช้งานทดสอบจนมั่นใจ
     (ทดสอบ: สร้างการแข่งขัน, กรอกคะแนน, รวมผล, export Excel, เปิด-ปิดระบบ)

ระยะที่ 3: Cut Over / สลับมาใช้จริง
  └─ ย้ายข้อมูลที่จำเป็น (ถ้ามี) → ประกาศใช้ AWS → แจกลิงก์ใหม่

ระยะที่ 4: ปิด Azure
  └─ เฝ้าดูระยะหนึ่งว่า AWS เสถียร → สำรองข้อมูล → ปิด/ลบ resource ฝั่ง Azure
```

**ข้อดีของวิธีนี้:** มีระบบสำรอง (Azure) ตลอดช่วงเปลี่ยนผ่าน หากพบปัญหาบน AWS ยังย้อนกลับไปใช้ Azure ได้ ความเสี่ยงต่ำ

| ความเสี่ยง | ระดับ | การรับมือ |
|-----------|:---:|-----------|
| ข้อมูลสูญหายช่วงย้าย | กลาง | สำรองข้อมูล (Export Excel + สำเนาไฟล์ฐานข้อมูล) ก่อน cut over; ไม่ปิด Azure จนกว่าจะมั่นใจ |

| ค่าใช้จ่ายเกินคาด | ต่ำ | ตั้ง Budget Alert บน AWS; ปิดระบบเมื่อไม่ใช้ |
| URL เปลี่ยน กรรมการเข้าไม่ได้ | ต่ำ | แจ้งล่วงหน้า + แจกลิงก์ใหม่ก่อนงาน |

## 10. ประเด็นที่ต้องการการตัดสินใจจากผู้ใช้งาน

กรุณาพิจารณาและให้คำตอบ เพื่อนำไปวางแผนลงมือ:

1. **รับรูปแบบ "เปิดระบบก่อนใช้ ปิดหลังใช้" เพื่อประหยัดได้ไหม?**
   หรือต้องการให้ออนไลน์ตลอดเวลา (ยอมจ่ายค่าคงที่รายเดือนเพิ่ม)?

2. **เรื่องข้อมูลเดิม** — ต้องการย้ายข้อมูลการแข่งขันเก่าทั้งหมด / เฉพาะบางส่วน / หรือเริ่มใหม่ได้?

3. **เรื่องโดเมน** — ใช้ URL ที่ AWS แจกให้ได้เลย หรือต้องการใช้ชื่อโดเมนขององค์กร?

4. **ช่วงเวลาที่เหมาะจะ cut over** — มีช่วงที่ไม่มีการแข่งขันให้สลับระบบอย่างปลอดภัยไหม?

## 11. ข้อเสนอแนะของทีมพัฒนา

แนะนำ **ทางเลือก A (ECS Fargate + EFS)** พร้อมรูปแบบ "เปิด-ปิดตามการใช้งาน"
เพราะตอบโจทย์ทั้ง "ต้องใช้ AWS" และ "ประหยัดสูงสุดสำหรับงานที่ใช้เป็นครั้งคราว" ได้ดีที่สุด
โดยไม่ต้องแก้ไขตัวโปรแกรม และมีแผนเปลี่ยนผ่านที่ปลอดภัย (ยังมี Azure เป็นสำรองระหว่างทาง)

หากในอนาคตปริมาณการใช้งานสูงขึ้นมาก สามารถอัปเกรดไปใช้ฐานข้อมูล RDS (ทางเลือก C) ได้ภายหลังโดยไม่ต้องรื้อระบบ
